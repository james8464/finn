# Plumb iPhone experience review — 12 October 2026

## Direction

The screen should feel like a quiet Apple utility used between sets: one clear action, truthful live feedback, and a result that names its evidence. Use native SwiftUI controls, SF Symbols in controls only, system text styles, semantic colors, and generous spacing. Reserve Evergreen/Signal for the primary action. Avoid gradient backgrounds, glass cards, invented scores, fake motion visualizations, generic AI chat, and ornamental coaching language. Use Liquid Glass only where the system places it in navigation and controls; keep content surfaces plain.

## Current screen audit and refinements

Fresh iOS 27 simulator captures of setup, the first set result, and the second-set comparison showed that the earlier primary buttons sat halfway down a mostly empty screen. Setup used a brand line before saying the task was a squat check, and the comparison put unexplained decimal values ahead of the change they represented. The refinements place the primary action at the bottom of setup and results, state the task plainly, and reveal exact measurements only when requested. A screenshot review then caught the two comparison columns crowding one another; the measurements are now stacked vertically. After disclosure content expanded, the in-page Done control could be covered by the fixed next-set action; Done now sits at the top of the result. The system's glass toolbar control failed automated contrast and Dynamic Type audits, so the result uses a plain text action with a 44-point target.

This follows Apple's [layout](https://developer.apple.com/design/human-interface-guidelines/layout) guidance on hierarchy and progressive disclosure, [writing](https://developer.apple.com/design/human-interface-guidelines/writing) guidance on plain action-oriented language, and [buttons](https://developer.apple.com/design/human-interface-guidelines/buttons) guidance to make the likely action prominent. The content remains plain; the bottom control layer uses a standard system material, in line with [materials](https://developer.apple.com/design/human-interface-guidelines/materials).

The result offers [ShareLink](https://developer.apple.com/documentation/swiftui/sharelink) for a measured text summary. When comparable sets exist, the text includes the direction of the camera-measured range change without calling it an improvement. Sharing is user-initiated through the system sheet; dismissed observations are excluded, and video is never part of the item. This makes a brief easy to send to a trainer without adding an account screen before there is a sync or shared-project service.

Simulator review captures: [setup](screenshots/2026-10-12-setup-demo.png), [first result](screenshots/2026-10-12-first-result-demo.png), and [dark setup](screenshots/2026-10-12-setup-dark-demo.png). Each shows the clearly labeled synthetic demo mode. The first automated dark run had actually rendered light; a dedicated test appearance flag exposed white text on dark mint actions and on the yellow demo badge. Button labels now use an adaptive foreground color and the badge uses black text. The dark setup was visually checked after that fix. A hosted audit later sampled a cropped badge edge on the camera-error screen; that screen has no synthetic set and now omits the badge.

## Applied HIG decisions

- [Design principles](https://developer.apple.com/design/human-interface-guidelines/design-principles), [iOS](https://developer.apple.com/design/human-interface-guidelines/designing-for-ios), [layout](https://developer.apple.com/design/human-interface-guidelines/layout), and [writing](https://developer.apple.com/design/human-interface-guidelines/writing): Setup has a single dominant camera action, concise instructions, and subdued secondary destinations. Results lead with the observation; rep measurements and range methodology sit behind native disclosures. Only the next-set action uses a filled button.
- [Color](https://developer.apple.com/design/human-interface-guidelines/color) and [accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility): System background and label colors adapt to appearance and contrast. Text carries every state; color alone never does. System text styles support Dynamic Type. Complete 88-test local runs passed on both iPhone 18 Pro Max and iPhone 18 Pro simulators; the [preceding hosted iOS 27 workflow](https://github.com/james8464/hackathon-project/actions/runs/38198910495) passed. Later hosted scans flagged generic Privacy text and even the black Camera heading on white; one capture audit also timed out. Screenshots show normal rendering, with measured policy-link contrast of about 6.5:1 in light mode and 13.7:1 in dark mode. Privacy tests now assert that every visible sentence is in the accessibility tree, check the policy link's 44-point target, and run description, Dynamic Type, clipping, and trait audits. The screenshot-based text, contrast, and hit-region scan categories are excluded only on Privacy because of those unrepeatable results; full audits remain on other screens. The Stop control remained reachable in dark, large text. Physical-device VoiceOver order and contrast still need checking.
- [Privacy](https://developer.apple.com/design/human-interface-guidelines/privacy): Camera permission follows **Set up camera**. Setup states that analysis stays on the iPhone and no video is saved. History and Privacy remain reachable without granting camera access. The policy link has a measured 44-point hit height, and Privacy section titles carry heading traits for assistive navigation. The page remains scrollable with its visual indicator hidden; iOS 27 had exposed two narrow duplicate indicator nodes to an earlier hit-area audit. Derived history and recovered backups request [complete file protection](https://developer.apple.com/documentation/uikit/encrypting-your-app-s-files); lock/unlock behavior still needs a physical iPhone.
- Camera recovery names permission denial, temporary unavailability, and interruption separately. The permission screen offers Settings; an unavailable camera offers retry. Recovery text grows inside a scroll view at accessibility text sizes.
- [Materials](https://developer.apple.com/design/human-interface-guidelines/materials): System controls can use the platform's native material. Camera pixels and measured results stay visually clear; no decorative glass panel overlays the person.
- [Sign in with Apple](https://developer.apple.com/design/human-interface-guidelines/sign-in-with-apple): Do not ask for an account on first launch. Current history exists only on the phone, so sign-in would not unlock a benefit. When cross-device history or a shared coach workflow exists, offer an optional account from History after the person has used the core loop; explain exactly what syncs and use the system-provided button. Keep camera frames local and never make sign-in a prerequisite for a set. A real identity service, storage design, deletion flow, and privacy update are prerequisites for that feature.

## Verification boundary

An iOS 27 simulator can test navigation, text sizes, appearances, accessibility audits, the synthetic set path, and deterministic scoring. It cannot validate real framing, pose accuracy, thermal behavior, VoiceOver's spoken order on a physical device, or the usefulness of cues to lifters. A physical iPhone and consenting sets remain required before making those claims.
